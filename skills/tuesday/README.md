# tuesday

The `tuesday` skill is how Tuesday's job-search modules are reached: one skill that reads a candidate's request, picks the one module the request needs, and runs that module from a copy of its instructions. The modules are [job-underwriter](../job-underwriter/) (whether to apply), [resume-tailor](../resume-tailor/) (a resume tailored to a named role) and [mock-interview](../mock-interview/) (interview prep and drills). Each module is still a complete skill of its own.

Part of [Tuesday](../../README.md), an applicant-side evidence system for job seekers. How to install it on each surface, and where it does not ship and why, is in that README's Install section. This README is for maintainers and ships nowhere (CONTRIBUTING.md, "Tuesday ships what was measured").

## Its routing role

Tuesday owns candidate-side job-search requests and runs exactly one module per turn. Its SKILL.md says how: a message that starts with a module's command, or names a module, runs that module (section 1); anything else is routed by a table of signals (section 2); a request that matches no row runs no module and is answered directly. A request that spans two modules runs the module for the first decision and names the other in one sentence, as `interaction-grammar.md` §6 asks of every skill. Its description carries its boundary: candidate-side only, and not for employers screening applicants, job-market questions, networking messages, resume design, proofreading, or shortening a resume with no target role.

Tuesday's row in the trigger-hygiene table of `interaction-grammar.md` §6 carries the boundary its description ends with. Its SKILL.md has no line pointing to that section's slash-command rule: the rule stops a module started by its own command from starting another skill, and Tuesday starts no skill at all, since it runs a module from its own `references/` (section 3).

## How references/ is made

Everything under `references/` is generated by `ci/sync.py` from the module skills' own files, and never edited here. A change goes into the module's file, and `python ci/sync.py` regenerates this folder. What CI holds this folder and SKILL.md to is in CONTRIBUTING.md ("Tuesday ships what was measured").

- **Playbooks.** `references/<module>.md` is that module's SKILL.md with its frontmatter stripped and a `## Contents` list of its `##` and `###` headings generated under its title. A playbook is read in full and runs past 100 lines, where the guidance asks a reference file to open with its contents; a SKILL.md body carries none, so the generator adds it rather than the module sources. A playbook and its files still say SKILL.md where they mean the module's own; Tuesday's section 3 says that SKILL.md there means the playbook being run.
- **Paths note.** After the contents list, each playbook gets one generated line, `PATHS_NOTE` in `ci/sync.py`: every `references/` path in the playbook means the folder that holds it, never a module's own skill folder, pointing to section 3, which states that rule. In Claude Code the hidden modules' folders sit beside Tuesday holding files of the same names, and in round 1's runs Haiku, after routing correctly, read a playbook's files from a hidden module's own folder (found while round 2 was built).
- **Copies.** Every file in a module's `references/` is carried in this one flat `references/`. A file several modules carry with identical text, as every convention mirror is, is carried once.
- **Name clashes.** Where two modules carry one file name with different text, or a module file is named like a playbook, each module's copy is carried as `<module>-<name>`. Every mention of the old name in that module's playbook and its own files, bare or under `references/`, is rewritten to the new one. Today that is each module's `rationale.md`, carried as `job-underwriter-rationale.md`, `mock-interview-rationale.md` and `resume-tailor-rationale.md`. The module sources keep their own names; only the generated copies move.
- **Refusals.** Generation stops rather than guess when a shared file names a clashing file, when a renamed file would overwrite another, or when a playbook names a file this folder would not carry.

`python ci/sync.py --list` lists each generated file and where it came from.

## Adding a module

A new module, such as a cover letter, is added in this order:

1. Write `skills/<module>/` as a standalone skill, with its own evals, its own description and its own row in `interaction-grammar.md` §6, so it uploads and runs alone.
2. Run `python ci/sync.py`, which adds `references/<module>.md` and the module's files to this folder.
3. Edit this skill's SKILL.md: the module's command in section 1, one routing row in section 2, its files in the reference index, and a clause in the description.
4. Measure routing again with the module's own positive and near-miss cases, since a new description changes every routing decision.
5. Record what was measured and move the plugin's version, as CONTRIBUTING.md says ("Tuesday ships what was measured").

The description is already 1,020 of the 1,024 characters a description may hold, so a fourth module means compressing every module's clause.
